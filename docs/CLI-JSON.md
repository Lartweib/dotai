# CLI JSON output

Every dotai command accepts the global `--json` flag. With it, the command prints exactly one JSON document, the **envelope**, to stdout. This is the contract scripts and a future UI build on ([0026](decisions/0026-json-cli-and-ui-after-v1.md)); changing it needs the same care as changing a flag.

## Envelope

Success:

```json
{
  "schema": "dotai.cli/v1",
  "command": "version",
  "ok": true,
  "data": { "version": "1.2.3", "commit": "…", "buildDate": "…", "goVersion": "go1.26.5", "os": "linux", "arch": "amd64" }
}
```

Failure:

```json
{
  "schema": "dotai.cli/v1",
  "command": "dotai",
  "ok": false,
  "error": { "code": "usage", "message": "unknown command \"nope\" for \"dotai\"" }
}
```

| Field | Meaning |
|---|---|
| `schema` | Envelope version. A breaking change to the envelope gets a new value. |
| `command` | Command path without the program name, for example `version`. `dotai` when no command was resolved. |
| `ok` | `true` on success, `false` on failure. |
| `data` | The command result. Always present when `ok` is `true`, as an object: `{}` when the command has no result, never `null`. When `ok` is `false`, present only with the `invalid` error code, where it holds the result that explains the failure, and for a `restore` refused over conflicts (`internal`), where it holds them; absent otherwise. Its shape is defined per command. |
| `error` | `code` and `message`. Present only when `ok` is `false`. |

Fields that are unknown, such as the commit of a local build, are empty strings, never omitted.

Any `--json` or `--json=<value>` argument requests JSON output, so an invalid value such as `--json=garbage` is reported as a `usage` envelope.

## Error codes and exit codes

| `error.code` | Exit code | When |
|---|---|---|
| — | 0 | Success. |
| `internal` | 1 | The command failed while running. |
| `usage` | 2 | Unknown command, unexpected argument or invalid flag. |
| `invalid` | 3 | The command read its input and rejected it, for example a pack with errors. `data` holds the result with the details. |

Without `--json`, results are plain text on stdout and errors go to stderr, with the same exit codes. One exception: in text mode an invalid pack (`validate`, `stage`, `rulesync fetch` or `install`) prints its report to stdout and nothing to stderr, because the report is the command's result; exit code 3 still signals the failure. `--format` chooses how they look and is ignored with `--json`:

- `pretty` (default): a summary header (`✗ <pack> <version> · 13 problems in 11 files`), then the diagnostics grouped by file in the order above, each with its `line:column` when it has one, its code and message, and the `first:` (related) and `fix:` (hint) lines.
- `compact`: one line per diagnostic, `file[:line[:column]]: code: message`, followed by ` (first: file[:line])` and ` (fix: hint)` when present, so editors can jump to the location.

A whole-file diagnostic (`line` `0`) prints no position in either format. Text output is colored only when stdout is a terminal that supports ANSI colors and `NO_COLOR` is unset or empty; `--json` output is never colored.

## Diagnostics

`validate`, `stage`, `rulesync fetch` and `install` report problems as `diagnostics`. Their stable contract is `code`, `file`, `line`, `column` and `related`: scripts may match on them, and changing them needs a new schema value. `message` and `hint` are text for people and may change in any release without a schema bump.

A diagnostic about a whole file, such as an item defined twice, has `line: 0` (and `column: 0`). Before any release these used `line: 1`; `dotai.cli/v1` is not released yet, so this change keeps the schema value.

Without `--json`, a download is announced on stderr as in `rulesync fetch`. A pack with errors fails with `invalid`, carries the same `data` and writes nothing. A missing `--out`, or an `--out` that is the pack directory or inside it, is a `usage` error. `<dir>` must be missing, empty, or an earlier staging, marked by a `.dotai-stage` file; an earlier staging is replaced as a whole only with `--force`, and any other non-empty directory is refused even with `--force` (`internal`). So a harness skipped once because it was not detected is managed again by the next install that detects it, and a harness of the saved choice that is not detected is skipped with a notice and stays in the choice. A required harness that is not detected fails with `internal` before anything is staged or written, naming it and why, such as `the pack requires antigravity-cli, which is not installed (agy not found on PATH)`; an optional harness that is not detected, or that `--harness` or the saved choice leaves out, is not managed, and a notice says why. `[]` when there is none); `harnesses`, every harness of the pack, the required ones and then the optional ones, in manifest order: each `id`, `required`, `managed` (whether the install manages it), its detection, `detected`, `binary` (the command as found on `PATH`, `""` when it is not), `config` (its configuration directory) and `configFound` (whether that is a directory), and, for a harness the install manages, what [0018](decisions/0018-install-modes-and-mandatory-backup.md) requires to show before installing; a harness it does not manage has `level`, `dir` and `relogin` `""` and the lists empty: `level` (`full`, `partial` or `none`), `dir` (its isolated directory), `pointers` (each `mechanism`, `env` for an environment variable or `flag` for a command-line flag, `name`, such as `CLAUDE_CONFIG_DIR` or `--gemini_dir`, and the `dir` it is set to), `relogin` (`yes` when the user must log in again, `no` when the login carries over, `unknown` on an OS where it was not verified: Claude Code's new login is verified on Windows only, where its credentials live in the configuration directory; `[]` when there is none); `pointers` and `leaks` depend on whether the variant shares skills: OpenCode's `OPENCODE_TEST_HOME` is a pointer only for one that does not; `ops`, in target order (with one exception, below): each `action` (`create` for a missing target, `replace` for one with other content or another exec bit, `unchanged`, `remove` for a file the previous install owned, by its [install state](#install-state), that the pack no longer stages and that is still there), `harness` (`""` for a tool, which installs to `<home>/.dotai/tools`), `source` (the path inside the user staging tree, `/`-separated, `""` for a `remove`), `target`, `exec` (the staged exec bit, `false` for a `remove`), `before` and `beforeExec` (the target's current SHA-256 in hex and exec bit, `""` and `false` when it is missing) `after` (the staged SHA-256, or for a harness's settings file the SHA-256 of what it is given, `""` for a `remove`) and `keys` (the keys the op writes into or deletes from a harness's settings file, each `key`, such as `model` or `env.DOTAI_TERMINAL`, and `action`, `create`, `replace` or `remove`; `diagnostics` as in `validate`. For a variant that shares skills, each skill of `sharedSkills` is a link for Claude Code (`<home>/.dotai/isolated/claude/skills/<name>`), with `source` its path in the user staging tree as if staged (`.claude/skills/<name>`), pointing at `<home>/.agents/skills/<name>`, the entry itself and not what it resolves to: a symbolic link, or on Windows a directory junction, which needs no administrator rights. agy skips a junction in its skills directory, so it gets a copy instead, on every OS: every file of the skill, the entry followed when it is a link but nothing below it, is copied into the user staging tree at `.gemini/antigravity-cli/skills/<name>/` and planned, owned, backed up and restored like the pack's files, at `<home>/.dotai/isolated/gemini/config/skills/<name>/`; a skill that holds anything that is neither a regular file nor a directory, or a name some OS cannot store, is not copied (`not-copyable`). Each install copies the skills again, so a changed skill is a `replace` and a skill that left the folder a `remove`, and a copy edited by hand is refused like any edited file. OpenCode reads the folder itself and gets neither. A link is planned like a file whose content is its destination: its `before` and `after` are the SHA-256 in hex of `link:` followed by the destination, it is `unchanged` when it already points there, `create`d when it is missing, and removed when an earlier install owned it and the skill left the folder, the pack now has a skill of that name or the variant no longer shares skills; a link dotai does not own that already points there is taken as it is, and one that points anywhere else fails with `internal`, naming where it points. Nothing ever follows a link to hash, back up, check or remove it. An owned link that points elsewhere was changed by hand: it is an edit, refused like an edited file. A link's destination is only ever `<home>/.agents/skills/<name of the link>` (compared without case on Windows and macOS): an install state, a journal or a backup manifest that records any other fails with `internal` before anything is written, and the destination is checked again right before each link is made, by an install, a restore or a rollback. A file where a link goes, or a link where a file goes, fails with `internal` (`... where the install needs a link`). A real directory where a link goes is taken only when every file it holds, found without following a link, is one the plan removes, such as the pack's skill of that name that the pack dropped; once they are removed, the directory, then empty, gives way to the link (an empty one does at once). One that holds anything else, such as a cache a harness wrote into the pack's skill directory, fails with `internal` before anything is written, naming the file (`<dir> holds <file>, which dotai did not install, where the link to the shared skill goes; ... move it away, then run again`); `restore` applies the same rule. An install killed after it removed a link and made the pack's directory there is settled by the next install or restore. A link the OS cannot make, on Windows one whose destination is not on a local drive, such as a home directory on a network share, which a junction cannot point at, fails with `internal` in the dry run, and in `install` and `restore` before anything is written. Ops are in target order, except that an op that removes a link comes before the ops below its path, and one that makes a link after them. A skill added to the shared folder after an install is linked by the next install. A file the previous install owned whose SHA-256 or exec bit is no longer what the install state records was edited by the user: it is neither replaced nor removed, and the plan fails with `internal`, naming every such file (a `--force` that overrides this does not exist yet); a file it owned that is missing is not an edit, and is created again when the pack still stages it. A harness's settings file (Claude Code's `settings.json`, agy's `antigravity-cli/settings.json` and OpenCode's `config/opencode/opencode.jsonc`, in their isolated directories) is planned key by key instead ([0035](decisions/0035-settings-files-owned-by-key.md)), since the harness writes into it too: dotai owns only the keys the pack puts there, each top-level key or each variable of Claude Code's `env`, as the settings merge identifies them. The target gets its own content with each key the pack stages set, a key the harness wrote included, and each key dotai owned that the pack no longer stages deleted, through an edit that keeps comments, key order and formatting; every other key stays, so a key the harness added is no reason to write. A missing target is created as staged; a file left with no key at all is removed; one in which dotai keeps no key, such as the file of a harness the pack dropped that holds keys the harness wrote, is written without dotai's keys and is no longer dotai's. A key dotai owns whose value is no longer what it wrote is an edit: the plan fails with `internal`, naming the key and the file (`the key model in <file> was changed after dotai installed it, and dotai does not overwrite it: put back the value dotai installed, or delete the key to take the pack's, then install again`); a key that is missing is not one, nor is a key that already holds the value the pack now stages, which the state then records. Deleting a key also deletes the comments on their own lines right above it, up to a blank line; the backup keeps the whole file. A settings file that is not a JSON or JSONC object fails with `internal`. An owned file outside `<home>/.dotai/isolated` and `<home>/.dotai/tools` (and, when the plan is in replace mode or follows a replace install, each harness's configuration directory), or an install state that cannot be read (another `schema`, a target that is not absolute or is owned twice), fails with `internal`. `root`, every `dir` and every `target` are absolute paths with the OS separator, as `path` in `rulesync fetch`. rulesync's sources (`.rulesync/`) are never planned. Every staged path is checked before the disk is read: a path Windows cannot store (a control character such as NUL, one of `:<>"|?*`, or a device name such as `CON`) fails with `internal` on every OS, and a staged file that no harness of the pack and no tools rule installs is a `path-unmapped` diagnostic at `dotai.yaml` (`line` `0`), one per file, naming it as `user/<path>`. Nothing on the way to a target is followed: each directory from the home directory down to the target must be a real directory or missing (a missing one means every target below it is `create`), and the target must be a regular file or missing. A link, a Windows junction or other reparse point, a file where a directory is needed, or a directory or other special file at a target fails with `internal`, naming that path and the fix: move or remove it, then plan again. The exception is a file the previous install owns on the old side of an adapter's move (agy's skills, which an older install put at `<home>/.dotai/isolated/gemini/antigravity-cli/skills/` and now install at `config/skills/`): when a link, junction or other special file is on its way, as agy may leave after it moves the directory, the file is taken as gone, neither read nor removed through it, and no longer owned. A pack with errors fails with `invalid` and carries the same `data` with empty `harnesses` and `ops`, and with the `mode` asked for or recorded and its `root`. A harness whose isolation level is `none` does not offer the isolated mode and fails with `internal`. Without `--json`, the plan is printed as a header with the pack, variant, mode and root, for a variant that shares skills a `shared skills: <dir> · <names>` line (or `<dir> is missing, so there is nothing to share`) followed by a `note:` line per skipped entry, and a `note:` line per notice; then each harness with its isolation level, whether it `needs a new login`, `keeps your login` or `may need a new login` (`unknown`), its `binary:` (or `not found on PATH`) and `config:` (followed by `(missing)` when it is not there) lines, each pointer (`NAME=<dir>` for a variable, `--flag=<dir>` for a flag, as the harness gets it), each leak and each tool command (`<key> runs tool <name>: <command>`); a harness the install does not manage is printed as `<id> · optional, not managed` with its `binary:` and `config:` lines only; then the operations grouped by harness in manifest order (a harness the pack no longer has, whose files are removed, after them) with the tools last, one `action  target` line each, with ` -> <destination>` after a link, followed under a settings file by the keys it writes, such as `keys: create env.DOTAI_TERMINAL, replace model`; and a final count, such as `16 create, 0 replace, 0 remove, 0 unchanged · dry run, nothing was written`. **Mode.** `--mode` is `isolated` or `replace`; any other value is a `usage` error, for a pack with problems too, since the mode is resolved before the pack is read. Without it, the install uses the `mode` of the [install state](#install-state), or `isolated` when there is none. `--mode isolated` over an install state whose `mode` is `replace` is a `usage` error, in the dry run too (`the install state records a replace install, and install does not switch it to isolated: run dotai restore to put your own configuration back first, then install --mode isolated`). **Replace mode** ([0038](decisions/0038-replace-mode-resets-harness-to-fresh-install.md)) resets each managed harness to a fresh install, then installs the pack in its own configuration directory: `<home>/.claude` for Claude Code, `<home>/.gemini` for agy, `<home>/.config/opencode` for OpenCode, and the tools in `<home>/.dotai/tools` as in the isolated mode.     { "target": "/home/u/.dotai/isolated/claude/CLAUDE.md", "harness": "claudecode", "sha256": "8e91…", "exec": false },
```json
    { "target": "/home/u/.dotai/isolated/claude/settings.json", "harness": "claudecode", "sha256": "5d0c…", "exec": false,
      "keys": [ { "path": ["model"], "sha256": "c2f4…" }, { "path": ["env", "DOTAI_TERMINAL"], "sha256": "07a9…" } ] },
    { "target": "/home/u/.dotai/isolated/claude/skills/review", "harness": "claudecode", "kind": "link", "link": "/home/u/.agents/skills/review", "exec": false },
    { "target": "/home/u/.dotai/tools/hello.sh", "harness": "", "sha256": "1e59…", "exec": true }
  ]

```

| Field | Meaning |
|---|---|
| `schema` | State version. A state with another value is not read: `install` fails with `internal`. |
| `pack` | The pack's `name` and `version`, and the absolute `path` it was installed from. |
| `variant`, `mode` | As in the plan. |
| `harnesses` | The harnesses the install manages, in manifest order. |
| `selection` | The `--harness` choice of the last install that was given one, or that reused one, in manifest order, which a plain `install` of the same pack reuses ([0038](decisions/0038-replace-mode-resets-harness-to-fresh-install.md)); absent when there is none. A state without it, as written before it existed, has no choice. |
| `sharedSkills` | Whether the variant shares the user's skills ([0036](decisions/0036-shared-skills-per-variant.md)), which `run` reads; added before any release, and a state without it reads as `false`. |
| `installedAt` | When the state was written, in UTC (RFC 3339). |
| `backup` | The id of the backup of the last install that wrote files, `""` when none did. |
| `files` | The ownership record, in target order: every file the install leaves in place, written or already `unchanged`, with its absolute `target`, `harness` (`""` for a tool), `sha256` and `exec` as written. A removed file is no longer listed. A link to a shared skill has `kind` `link` and `link`, its destination, instead of `sha256`, and `exec` `false`; any other record has no `kind`. A harness's settings file also has `keys`, the keys dotai owns in it ([0035](decisions/0035-settings-files-owned-by-key.md)), never empty: each `path`, the top-level key or `["env", "<VAR>"]` for a variable of Claude Code's `env`, and the `sha256` of its value as canonical JSON (compact, object keys sorted, numbers as written); the rest of the file is the harness's, and a settings file in which dotai keeps no key is not listed. `keys` was added before any release, without a new schema: a settings file without it was recorded whole by an earlier install, and the next install owns every key of it when it is still as written, and refuses it as edited otherwise. |
| `pending` | Present only while an install is writing, and left behind when it was killed or its rollback failed: the journal, with its `backup` id and `ops`, each `action`, `target`, `harness`, and `before` and `after` as in the backup manifest (a link as its `link`), and for a settings file `keys`, the keys dotai owns there once the op is written (absent when it owns none). `files` is then what dotai owned before that install. |

A `restore` writes the same journal, with the id of its own backup, so that a restore that was killed is settled by the next restore, as above, or by the next install like an install that was. An install that settles a restore's journal records the backup the state names, not the restore's.

The next install, and `install --dry-run`, read a target of `pending` as dotai's when it holds what `files` or `pending` says dotai wrote; a target dotai did not own before that still holds what `pending` records as `before` is the user's own file again, so it is neither an edit nor removed. Any other content is an edit, as for `files`. In a settings file, the keys of `pending` are dotai's when the file holds what `pending` wrote, or when it holds them as written after the harness wrote another key; otherwise the keys of `files` are checked. The install that follows drops `pending`.

## Backups

Each `install` that writes a file first takes a backup in `<home>/.dotai/backups/<id>/`, as [0018](decisions/0018-install-modes-and-mandatory-backup.md) describes. The id is the UTC time with milliseconds and the operation, such as `20261029T101501.874Z_install`, so ids sort in time order and are valid file names on Windows. Backup directories are created `0700` and their files `0600`. A `restore` that writes files takes one too, `<timestamp>_restore`, of every file it replaces or deletes. A backup holds `manifest.json`, `state.json` when there was an install state before the operation (a copy of it, synced like the rest) and, under `files/`, a copy of each target that is replaced or removed, at its path relative to the home directory (for example `files/.dotai/tools/hello.sh`), so that it can be restored by hand. Only plan targets are ever copied: nothing else in an isolated directory, such as a harness's credentials, is backed up.

```json
{
  "schema": "dotai.backup/v1",
  "id": "20261029T101501.874Z_install",
  "operation": "install",
  "createdAt": "2026-10-29T10:15:01.874Z",
  "home": "/home/u",
  "mode": "isolated",
  "pack": { "name": "minimal-pack", "version": "0.1.0", "path": "/home/u/packs/minimal-pack" },
  "variant": "standalone",
  "harnesses": ["claudecode", "antigravity-cli", "opencode"],
  "priorState": { "file": "state.json", "sha256": "4b2f…" },
  "ops": [
    { "action": "create", "target": "/home/u/.dotai/isolated/claude/CLAUDE.md", "after": { "sha256": "8e91…", "exec": false } },
    { "action": "replace", "target": "/home/u/.dotai/tools/hello.sh", "file": "files/.dotai/tools/hello.sh",
      "before": { "sha256": "77ac…", "exec": true }, "after": { "sha256": "1e59…", "exec": true } },
    { "action": "remove", "target": "/home/u/.dotai/isolated/claude/rules/old.md", "file": "files/.dotai/isolated/claude/rules/old.md",
      "before": { "sha256": "c0de…", "exec": false } }
  ]
}
```

`priorState` is the install state from before the operation: `file` (`state.json` in the backup) and its `sha256`, or `{ "none": true }` when there was none; restore puts it back, and finds the install before through its `backup`. Backups taken before `priorState` existed lack it, and restore refuses them. `restored`, added by the restore that undid the install, holds `at` (UTC) and `backup`, that restore's backup id (`""` when it wrote no file). `ops` lists every target the install writes, in target order (with the exception `install` makes for links); `unchanged` targets are left out. `before` is what the target had, absent for a `create`; `after` is what it is given, absent for a `remove`; each holds `sha256` and `exec`, or for a link to a shared skill `link`, its destination, and `exec` `false`, without `sha256`; `file` is the copy inside the backup, present for a `replace` and a `remove` of a file, never for a link, which restore makes again from its `link`. A created target has no copy, so that a restore deletes it. The manifest is written after every copy, so a backup without one is incomplete; the copies, the manifest and their directories are synced to the disk (directories where the OS can) before the install writes anything else. After a successful install or restore, backups are pruned: complete backups are ordered by the `createdAt` of their manifests, then by id, so a clock that went back does not reorder them, and at most 10 are kept besides the oldest, which is never deleted. The backups the install state leads to (the one it names, then the one each kept `priorState` names) are pruned last: restored installs and restore backups go first, oldest first, and of that history only what is beyond its newest 10 goes, so a restore can always reach back 10 installs. The backup just taken and the one the install state names are never deleted. A backup without a manifest does not count and is deleted, since under the lock only an install that stopped can have left it; a backup whose manifest cannot be read is left alone, and directories whose names are not backup ids are never touched. A restore's backup lists, in the order it writes them, each file it puts back (`create` for one that was missing, `replace`) or deletes (`remove`), with `before` as the disk held it.
