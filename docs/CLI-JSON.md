# CLI JSON output

Every dotai command accepts the global `--json` flag. With it, the command prints exactly one JSON document, the **envelope**, to stdout. This is the contract scripts and a future UI build on ([0026](decisions/0026-json-cli-and-ui-after-v1.md)); changing it needs the same care as changing a flag.

## Envelope

Success:

```json
{
  "schema": "dotai.cli/v1",
  "command": "version",
  "ok": true,
  "data": { "version": "1.2.3", "commit": "…", "buildDate": "…", "goVersion": "go1.26.5", "os": "linux", "arch": "amd64" }
}
```

Failure:

```json
{
  "schema": "dotai.cli/v1",
  "command": "dotai",
  "ok": false,
  "error": { "code": "usage", "message": "unknown command \"nope\" for \"dotai\"" }
}
```

| Field | Meaning |
|---|---|
| `schema` | Envelope version. A breaking change to the envelope gets a new value. |
| `command` | Command path without the program name, for example `version`. `dotai` when no command was resolved. |
| `ok` | `true` on success, `false` on failure. |
| `data` | The command result. Always present when `ok` is `true`, as an object: `{}` when the command has no result, never `null`. When `ok` is `false`, present only with the `invalid` error code, where it holds the result that explains the failure, for a `restore` refused over conflicts (`internal`), where it holds them, for a `doctor --fix` that failed midway (`internal`), where it holds what doctor found and fixed before, and with the codes of a refused replace install, restore or project apply below (`consent-required`, `replace-refused`, `harness-running`, `apply-refused`); absent otherwise. Its shape is defined per command. |
| `error` | `code` and `message`. Present only when `ok` is `false`. |

Fields that are unknown, such as the commit of a local build, are empty strings, never omitted.

Any `--json` or `--json=<value>` argument requests JSON output, so an invalid value such as `--json=garbage` is reported as a `usage` envelope.

## Error codes and exit codes

| `error.code` | Exit code | When |
|---|---|---|
| — | 0 | Success. |
| `internal` | 1 | The command failed while running. |
| `usage` | 2 | Unknown command, unexpected argument or invalid flag. |
| `invalid` | 3 | The command read its input and rejected it, for example a pack with errors, or `doctor` found a problem. `data` holds the result with the details. |
| `consent-required` | 1 | A replace install would wipe or overwrite what dotai does not own, and was not allowed to: no `--yes`, and no terminal to ask on or `--json` ([0038](decisions/0038-replace-mode-resets-harness-to-fresh-install.md)). `data` is the install plan. The install wrote nothing, though a move across volumes that a killed install left may have been settled first. |
| `replace-refused` | 1 | A replace install whose plan has `refusals`, which `--yes` does not override. `data` is the install plan with them. The install wrote nothing, as above. |
| `apply-refused` | 1 | A project apply whose plan has `refusals`, which `--yes` does not override, such as a Claude Code MCP server whose name a server dotai did not add already has ([0041](decisions/0041-project-scope-local-and-untracked.md)). `data` is the project plan. Nothing was written. A project apply that would overwrite a conflict without consent fails with `consent-required`, with the project plan in `data`. |
| `record-invalid` | 1 | The project's record under the home directory names what an apply of the project never writes, such as a target outside the project a backup outside its backups, or an exclude entry not anchored at the project or holding a line break ([0041](decisions/0041-project-scope-local-and-untracked.md)). `apply`, its dry run and `restore --project` refuse it before anything is written. No `data`. |
| `project-refused` | 1 | A project apply in the home directory or at the root of a drive or of the file system, where the project scope would overlap the user scope ([0041](decisions/0041-project-scope-local-and-untracked.md)). No `data`; nothing was written. |
| `harness-running` | 1 | A replace install, or a restore that writes into a harness's own configuration, while a harness it writes into is running, without `--ignore-running`. `data`: `harnesses`, those checked, and `running`, each process found, `harness`, `pid` and `name`, `[]` when the processes could not be listed, which refuses too. The install or restore wrote nothing, as above. |

Without `--json`, results are plain text on stdout and errors go to stderr, with the same exit codes. One exception: in text mode an invalid pack (`validate`, `stage`, `rulesync fetch` or `install`), and a `doctor` that finds a problem, print the report to stdout and nothing to stderr, because the report is the command's result; exit code 3 still signals the failure. `--format` chooses how they look and is ignored with `--json`:

- `pretty` (default): a summary header (`✗ <pack> <version> · 13 problems in 11 files`), then the diagnostics grouped by file in the order above, each with its `line:column` when it has one, its code and message, and the `first:` (related) and `fix:` (hint) lines.
- `compact`: one line per diagnostic, `file[:line[:column]]: code: message`, followed by ` (first: file[:line])` and ` (fix: hint)` when present, so editors can jump to the location.

A whole-file diagnostic (`line` `0`) prints no position in either format. Text output is colored only when stdout is a terminal that supports ANSI colors and `NO_COLOR` is unset or empty; `--json` output is never colored.

## Diagnostics

`validate`, `stage`, `rulesync fetch` and `install` report problems as `diagnostics`. Their stable contract is `code`, `file`, `line`, `column` and `related`: scripts may match on them, and changing them needs a new schema value. `message` and `hint` are text for people and may change in any release without a schema bump.

A diagnostic about a whole file, such as an item defined twice, has `line: 0` (and `column: 0`). Before any release these used `line: 1`; `dotai.cli/v1` is not released yet, so this change keeps the schema value.

`validate` also reports `warnings`, with the same fields and the same stable contract; a warning never makes a pack invalid. Its codes so far are `hooks-shadowed` and `mod-matcher-bare`; the set may grow in any release, so a script should accept a warning code it does not know. A warning's `related` is the other place involved: for `hooks-shadowed`, the event in the shared hooks that the block's event replaces.

`apply --dry-run` reports its own `warnings`, each `code`, `harness`, `item`, `path` and `message`, with the same stable contract for all but `message`: `exclude-pending`, `no-local-slot`, `scope-clash` and `read-twice` so far (see the `apply` row); the set may grow, as for `validate`. `apply --dry-run` and `apply` add `marker-mismatch`, and `apply` adds `mcp-keys-lost` and `cleanup-failed`. Their `refusals` have the same fields and contract, with the codes `mcp-server-foreign` and `marker-tracked` so far.

`stage` and `install` also report `hook-path-unquotable`, which `validate` cannot, since it depends on the home or project directory ([0037](decisions/0037-tool-commands-resolved-per-os.md)).

Before any release, `validate` reported `merge-pending` for `.rulesync/hooks.jsonc` or `.rulesync/permissions.jsonc` in two layers of a scope. Those files now merge ([0040](decisions/0040-list-files-merged-as-a-union.md)), and the code is removed, not reserved; `dotai.cli/v1` is not released yet, so this change keeps the schema value.

## Doctor findings

The `code` of each finding of `doctor`. Codes are stable, as diagnostic codes are; `message` is text for people. The set may grow, so a script should accept a code it does not know. Every finding that is not `fixed` counts as a problem.

| Code | Fixable | Meaning |
|---|---|---|
| `file-changed` | no | A file dotai owns whole holds something else, a link points elsewhere, or a file merged by key is no longer a JSON object. |
| `file-missing` | no | A file dotai owns is gone. |
| `key-changed` | no | A key dotai owns in a settings file or a file merged by key holds another value. A key of a harness's home file that a valid record of another worktree says dotai wrote with that value, as the worktrees of a repository own Claude Code's MCP servers jointly, is not reported. |
| `key-missing` | no | A key dotai owns is gone, such as an MCP server from Claude Code's `.claude.json`. |
| `marker-mismatch` | no | The project marker is missing or does not say what the record says; the record wins. |
| `record-invalid` | no | A record that is not one an apply of its project writes, such as one whose exclude entries are not patterns anchored at the project or hold a line break, or that is not in the directory of its project's id. | `orphan-entry` | no | An entry of `projects.json` whose project directory or record is gone; the keys it lists stay until removed by hand. |

## Install state

`install` records what it installed in `<home>/.dotai/state.json` ([0032](decisions/0032-install-state-backup-and-isolated-launch.md)), readable by the user only (`0600`) and always written atomically (a temporary file in `<home>/.dotai/` moved over it). It is not an envelope, and `install --dry-run` and the next `install` read it for its ownership record.

```json
{
  "schema": "dotai.state/v1",
  "pack": { "name": "minimal-pack", "version": "0.1.0", "path": "/home/u/packs/minimal-pack" },
  "variant": "shared",
  "sharedSkills": true,
  "mode": "isolated",
  "installedAt": "2026-10-29T10:15:02.31Z",
  "harnesses": ["claudecode", "antigravity-cli", "opencode"],
  "backup": "20261029T101501.874Z_install",
  "files": [
    { "target": "/home/u/.dotai/isolated/claude/CLAUDE.md", "harness": "claudecode", "sha256": "8e91…", "exec": false },
    { "target": "/home/u/.dotai/isolated/claude/settings.json", "harness": "claudecode", "sha256": "5d0c…", "exec": false,
      "keys": [ { "path": ["model"], "sha256": "c2f4…" }, { "path": ["env", "DOTAI_TERMINAL"], "sha256": "07a9…" } ] },
    { "target": "/home/u/.dotai/isolated/claude/skills/review", "harness": "claudecode", "kind": "link", "link": "/home/u/.agents/skills/review", "exec": false },
    { "target": "/home/u/.dotai/tools/hello.sh", "harness": "", "sha256": "1e59…", "exec": true }
  ]
}
```

| Field | Meaning |
|---|---|
| `schema` | State version. A state with another value is not read: `install` fails with `internal`. |
| `pack` | The pack's `name` and `version`, and the absolute `path` it was installed from. |
| `variant`, `mode` | As in the plan. |
| `harnesses` | The harnesses the install manages, in manifest order. |
| `selection` | The `--harness` choice of the last install that was given one, or that reused one, in manifest order, which a plain `install` of the same pack reuses ([0038](decisions/0038-replace-mode-resets-harness-to-fresh-install.md)); absent when there is none. A state without it, as written before it existed, has no choice. |
| `sharedSkills` | Whether the variant shares the user's skills ([0036](decisions/0036-shared-skills-per-variant.md)), which `run` reads; added before any release, and a state without it reads as `false`. |
| `installedAt` | When the state was written, in UTC (RFC 3339). |
| `backup` | The id of the backup of the last install that wrote files, `""` when none did. |
| `files` | The ownership record, in target order: every file the install leaves in place, written or already `unchanged`, with its absolute `target`, `harness` (`""` for a tool), `sha256` and `exec` as written. A removed file is no longer listed. A link to a shared skill has `kind` `link` and `link`, its destination, instead of `sha256`, and `exec` `false`; any other record has no `kind`. A harness's settings file also has `keys`, the keys dotai owns in it ([0035](decisions/0035-settings-files-owned-by-key.md)), never empty: each `path`, the top-level key or `["env", "<VAR>"]` for a variable of Claude Code's `env`, and the `sha256` of its value as canonical JSON (compact, object keys sorted, numbers as written); the rest of the file is the harness's, and a settings file in which dotai keeps no key is not listed. `keys` was added before any release, without a new schema: a settings file without it was recorded whole by an earlier install, and the next install owns every key of it when it is still as written, and refuses it as edited otherwise. |
| `pending` | Present only while an install is writing, and left behind when it was killed or its rollback failed: the journal, with its `backup` id and `ops`, each `action`, `target`, `harness`, and `before` and `after` as in the backup manifest (a link as its `link`), and for a settings file `keys`, the keys dotai owns there once the op is written (absent when it owns none). `files` is then what dotai owned before that install. A replace install ([0038](decisions/0038-replace-mode-resets-harness-to-fresh-install.md)) also lists `wipes`, the absolute paths of the entries it moves into its backup, and `splits`, the files it rewrites by key, such as `~/.claude.json`, both absent when there is none; neither is ever dotai's. It writes its journal first with `ops` empty, and with them only once every entry is moved and every split file written, so that an install killed while it wipes wrote none of the pack's files and owns nothing of what it had not moved yet: the next install wipes what is left into its own backup, which leads to the killed one's. A restore's journal lists in `wipes` the paths it moves entries back to. |

A `restore` writes the same journal, with the id of its own backup, so that a restore that was killed is settled by the next restore, as above, or by the next install like an install that was. An install that settles a restore's journal records the backup the state names, not the restore's.

The next install, and `install --dry-run`, read a target of `pending` as dotai's when it holds what `files` or `pending` says dotai wrote; a target dotai did not own before that still holds what `pending` records as `before` is the user's own file again, so it is neither an edit nor removed. Any other content is an edit, as for `files`. In a settings file, the keys of `pending` are dotai's when the file holds what `pending` wrote, or when it holds them as written after the harness wrote another key; otherwise the keys of `files` are checked. The install that follows drops `pending`.

## Backups

Each `install` that writes a file first takes a backup in `<home>/.dotai/backups/<id>/`, as [0018](decisions/0018-install-modes-and-mandatory-backup.md) describes. The id is the UTC time with milliseconds and the operation, such as `20261029T101501.874Z_install`, so ids sort in time order and are valid file names on Windows. Backup directories are created `0700` and their files `0600`. A `restore` that writes files takes one too, `<timestamp>_restore`, of every file it replaces or deletes. A backup holds `manifest.json`, `state.json` when there was an install state before the operation (a copy of it, synced like the rest) and, under `files/`, a copy of each target that is replaced or removed, at its path relative to the home directory (for example `files/.dotai/tools/hello.sh`), so that it can be restored by hand. Only plan targets are ever copied: nothing else in an isolated directory, such as a harness's credentials, is backed up.

```json
{
  "schema": "dotai.backup/v1",
  "id": "20261029T101501.874Z_install",
  "operation": "install",
  "createdAt": "2026-10-29T10:15:01.874Z",
  "home": "/home/u",
  "mode": "isolated",
  "pack": { "name": "minimal-pack", "version": "0.1.0", "path": "/home/u/packs/minimal-pack" },
  "variant": "standalone",
  "harnesses": ["claudecode", "antigravity-cli", "opencode"],
  "priorState": { "file": "state.json", "sha256": "4b2f…" },
  "ops": [
    { "action": "create", "target": "/home/u/.dotai/isolated/claude/CLAUDE.md", "after": { "sha256": "8e91…", "exec": false } },
    { "action": "replace", "target": "/home/u/.dotai/tools/hello.sh", "file": "files/.dotai/tools/hello.sh",
      "before": { "sha256": "77ac…", "exec": true }, "after": { "sha256": "1e59…", "exec": true } },
    { "action": "remove", "target": "/home/u/.dotai/isolated/claude/rules/old.md", "file": "files/.dotai/isolated/claude/rules/old.md",
      "before": { "sha256": "c0de…", "exec": false } }
  ]
}
```

`priorState` is the install state from before the operation: `file` (`state.json` in the backup) and its `sha256`, or `{ "none": true }` when there was none; restore puts it back, and finds the install before through its `backup`. Backups taken before `priorState` existed lack it, and restore refuses them. `restored`, added by the restore that undid the install, holds `at` (UTC) and `backup`, that restore's backup id (`""` when it wrote no file). `ops` lists every target the install writes, in target order (with the exception `install` makes for links); `unchanged` targets are left out. `before` is what the target had, absent for a `create`; `after` is what it is given, absent for a `remove`; each holds `sha256` and `exec`, or for a link to a shared skill `link`, its destination, and `exec` `false`, without `sha256`; `file` is the copy inside the backup, present for a `replace` and a `remove` of a file, never for a link, which restore makes again from its `link`. A created target has no copy, so that a restore deletes it. The manifest is written after every copy, so a backup without one is incomplete; the copies, the manifest and their directories are synced to the disk (directories where the OS can) before the install writes anything else. After a successful install or restore, backups are pruned: complete backups are ordered by the `createdAt` of their manifests, then by id, so a clock that went back does not reorder them, and at most 10 are kept besides the oldest, which is never deleted. The backups the install state leads to (the one it names, then the one each kept `priorState` names) are pruned last: restored installs and restore backups go first, oldest first, and of that history only what is beyond its newest 10 goes, so a restore can always reach back 10 installs. The backup just taken and the one the install state names are never deleted. A backup without a manifest does not count and is deleted, since under the lock only an install that stopped can have left it; a backup whose manifest cannot be read is left alone, and directories whose names are not backup ids are never touched. A restore's backup lists, in the order it writes them, each file it puts back (`create` for one that was missing, `replace`) or deletes (`remove`), with `before` as the disk held it.

A replace install ([0038](decisions/0038-replace-mode-resets-harness-to-fresh-install.md)) moves each entry it wipes into its backup instead of copying it: a rename inside the home directory to `files/<path relative to the home directory>`, which keeps links and junctions as they are, never followed, permissions, timestamps and empty directories; across volumes, the entry is copied, checked and its source deleted instead, as `install` describes. The manifest lists each one under `wipes`, in the order it is moved: `harness`, `path` (absolute), `kind` (`file`, `dir` or `link`), `file` (where it is in the backup) and `items`, the entry itself (`path` `""`) and, for a directory, everything inside it, without following a link, each `path` (slash path inside the entry), `kind`, for a file `sha256` and `exec`, for a link `link`, its destination (`""` for a reparse point that is not a junction). The manifest is written before the first move, so a backup that holds moved entries always has one, and written again with the `items` of each entry once every entry is moved, read from the backup, before the pack's files are written, so that a file a harness still running changed before its entry moved is recorded as it was moved; an install killed before then leaves `items` absent, and restore reads them from the backup, taking whatever stands at the path of an entry it never moved as that entry. `splits` lists each file whose configuration keys it deletes, keeping every other byte: `harness`, `target`, `file` (the copy of what it held, under `files/`), `before` and `after` (`sha256`, `exec`) and `keys`, each a path from the top of the file. dotai never owns such a file, so it is in neither `ops` nor the state's `files`. A restore of a replace install records in its own backup the entries it moved out of the way under `wipes`, with `file` `moved/<install backup id>/<path>`, and the split files it wrote under `splits`, `file` and `before` absent when the file was missing.

The pinned backup is the oldest of the replace installs that the install state leads back to, through each `priorState`, without a backup of another mode in between: the first replace backup, which holds the configuration from before dotai. It is read from that history and recorded nowhere, so that a replace install that failed and rolled back, which the history no longer leads to, is never it, and one that was killed and settled by the next install is, since its backup holds what it moved. Retention never prunes it, nor the backups from the one the install state names back to it. A restore that undoes it releases it, and the next replace install is pinned in turn. Every replace install wipes again: what was put in a wiped area since goes into that install's backup, which is not pinned.

A project apply, `doctor --fix` and `restore --project` ([0041](decisions/0041-project-scope-local-and-untracked.md)) take their backups in `<home>/.dotai/projects/<project id>/backups/<id>/`, where the project id is the first 16 hex digits of the SHA-256 of the project's path (in lower case where paths are compared without case, on Windows and macOS), outside the project, so that a clean of the worktree, or the restore, which removes `.dotai/`, keeps them. Their ids end in `_apply`, `_fix` or `_restore`, and the manifest's `operation` is the same, `apply`, `fix` or `restore`. Each holds `manifest.json`, `record.json`, the project record from before the operation when there was one, and under `files/` a copy of each target it overwrote or deleted:

```json
{
  "schema": "dotai.project-backup/v1",
  "id": "20261102T101501.874Z_apply",
  "operation": "apply",
  "createdAt": "2026-11-02T10:15:01.874Z",
  "project": "/work/site",
  "copies": [
    { "target": "/work/site/.claude/settings.local.json", "file": "files/0", "sha256": "4b2f…", "exec": false },
    { "target": "/work/site/.git/info/exclude", "file": "files/1", "sha256": "c0de…", "exec": false }
  ]
}
```

A harness's home file whose keys the apply edits, such as `~/.claude.json`, is copied there too, for the user only: a restore never puts it back whole, since the record keeps the value each key had before. These backups are not pruned yet.

## Web UI API

`dotai ui` serves a JSON API on `127.0.0.1` for the local web UI ([0043](decisions/0043-local-web-ui.md)). Its handlers call the same use cases as the commands, and every response is the envelope above, with the same `data` and error codes as the command it names in `command`. Only the actions write in the home directory or in a project: install, apply, restore, restore of a project and `doctor --fix`, each one for a plan it was shown first (see [Plan, then confirm](#plan-then-confirm)). A plan fetches the rulesync binary its pack pins into the rulesync cache, stages the pack into a temporary directory that it removes, and, for a project, runs git there, as `--dry-run` does; nothing else is written.

Every request is checked before it reaches an endpoint:

- **Host**: it must be `127.0.0.1:<port>` or `localhost:<port>`, the server's own, so that a page that points its own name at `127.0.0.1` (DNS rebinding) is refused.
- **Origin**: when present, it must be `http://127.0.0.1:<port>` or `http://localhost:<port>`; a `Sec-Fetch-Site` of `cross-site` or `same-site` is refused too, so that no other page can call the API (CSRF).
- **Session token**: every API request except `POST /api/session` carries `Authorization: Bearer <token>`. No cookie is a credential, since a browser sends the cookies of `127.0.0.1` to every port.

Each run makes two secrets of 32 bytes from `crypto/rand`: a one-time code and the session token. The address `dotai ui` prints carries the code in its fragment, `http://127.0.0.1:<port>/#code=<code>`, which the browser never sends to the server or in a `Referer`. To open the browser, `dotai ui` does not pass that address on a command line, which other users may read: it writes a page that sends the browser there, readable by the user alone (`0600`, in a new `0700` directory of the temporary directory), opens the page's path, and deletes the page once the code is traded or when it stops. The embedded page takes the code out of the address with `history.replaceState`, posts it to `/api/session`, and keeps the token it gets back in `sessionStorage`. The code is good for one exchange, within two minutes of the start: a second exchange is refused with `unauthorized` and "this link was already used; restart dotai ui", and a late one with "this link expired". A wrong code is refused and leaves the code good. The embedded frontend itself is public and needs no token.

| Method and path | `command` | Input | `data` |
|---|---|---|---|
| `POST /api/session` | `ui` | Body `{"code": "<code>"}` | `token`: the session token. |

A body must be one JSON object sent as `application/json`, with no unknown field. A required parameter that is missing, a path that is not absolute or a body that does not fit is a `usage` error. Each path takes one method; another is refused with `405` and an `Allow` header naming it. Only one plan or action runs at a time: one asked for while another runs is refused at once with `busy` (429), not queued, and one that runs longer than five minutes is stopped and fails with `internal`; an action stopped that way rolls back what it wrote, as on the command line. The HTTP status follows the error code: `usage` 400, `invalid` 422, the refusals of the command line (`consent-required`, `replace-refused`, `harness-running`, `apply-refused`, `project-refused`, `record-invalid`) 409, `plan-changed` 409, and `internal` or any other code 500. The API adds six codes of its own, with `command` `ui` when no endpoint was reached:

| `error.code` | HTTP status | When |
|---|---|---|
| `unauthorized` | 401 | The request carries no session token, or not the one of this run; or the one-time code is wrong, used or expired. |
| `forbidden` | 403 | The Host is not the server's, or the request comes from another origin or site. |
| `not-found` | 404 | No endpoint has that path. |
| `method-not-allowed` | 405 | The endpoint does not take that method. |
| `busy` | 429 | A plan or an action was asked for while another one runs. |
| `plan-changed` | 409 | The plan an action is about to carry out is not the one of its `digest`. Nothing of the plan was written; `data` is the new plan, with its own `digest`. |

Outside `/api/`, the server serves the embedded frontend; a refused request there gets the reason as plain text.

### Plan, then confirm

Every plan and preview (`POST /api/install/plan`, `POST /api/apply/plan`, `GET /api/restore/preview`, `GET /api/restore/project/preview` and `GET /api/doctor`) adds `digest` to its `data`: `sha256:` and the SHA-256 in hex of the JSON of the plan without that field. The action takes the same choices back with that `digest`. The use case plans again, as the command does, and asks the server with that plan before it checks a running harness, asks for consent, takes the lock or writes. When the new plan has another digest, because a file, the state or the pack changed in between, the action stops with `plan-changed` (409) and the new plan with its `digest` in `data`, so that the page shows it and the user confirms it again. An action carries out a plan only when the plan is the one the user saw. What the action settles before it plans, a cut-short move across volumes or the journal of an interrupted apply, is settled as on the command line.

`yes` is the consent of `--yes`: without it, an action whose plan overwrites what dotai does not own fails with `consent-required` and writes nothing. The actions never skip the running-harness check (`--ignore-running`).
