# Harness notes

Verified behavior of the v1 harnesses that the adapters rely on. Each fact names the version it was checked on; harnesses change often, so re-check before relying on a fact for a new version. Decisions built on these facts are linked.

## Claude Code (2.1.x)

- **Rules files:** there is no user-level `AGENTS.md`. A project `AGENTS.md` loads only when there is no `CLAUDE.md` ([0012](decisions/0012-rules-file-per-harness.md)). On 2.1.316, in an isolated configuration directory, a project `AGENTS.md` alone did not load at all; an import does load it (see the [project scope inventory](#project-scope-inventory)).
- **MCP:** a `mcpServers` block in `settings.json` is not loaded. MCP servers go in `.mcp.json` (project) or `~/.claude.json` (user).
- **`PreToolUse` hook on `Agent`:** `tool_input` includes `model` only when the model sends it, so a hook can detect a missing model. Effort is not in `tool_input`; the session effort is the top-level `effort.level` field (also `$CLAUDE_EFFORT`). `updatedInput` can set `model` (checked with the `sonnet` alias) and must copy every original field. Effort cannot be set per launch ([0024](decisions/0024-models-declared-per-harness-no-tiers.md)).
- **Settings:** `~/.claude/settings.json` and `.claude/settings.json`; the schema rejects unknown keys ([0025](decisions/0025-settings-as-per-harness-passthrough.md)).
- **Plugins** cannot carry `CLAUDE.md`, the main `statusLine`, permissions or `env`. A mod is a plugin with a hooks module. Inside a plugin, agents become `<plugin>:<agent>` and MCP tools `mcp__plugin_<plugin>_<server>__<tool>`. A plugin under `.claude/skills/<name>/` with a `.claude-plugin/plugin.json` loads at project scope after workspace trust; installing from a marketplace with `--scope project` writes state under the user configuration directory (checked on 2.1.310, [0027](decisions/0027-loose-files-and-plugins-only-for-mods.md)).
- **Isolation:** `CLAUDE_CONFIG_DIR` is partial ([0018](decisions/0018-install-modes-and-mandatory-backup.md)).
- **Variables (documented, [environment variables](https://code.claude.com/docs/en/env-vars), read 2026-11-04, not checked at runtime):** `CLAUDE_CODE_PLUGIN_DIRS` loads plugin directories as `--plugin-dir` does; `CLAUDE_CODE_PLUGIN_SEED_DIR` names read-only plugin seed directories; `CLAUDE_CODE_PLUGIN_CACHE_DIR` moves the plugins root, `~/.claude/plugins` by default; `CLAUDE_ENV_FILE` is a shell script run before each Bash command. Claude Code sets `CLAUDECODE=1`, `CLAUDE_CODE_CHILD_SESSION=1`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_EFFORT`, `CLAUDE_CODE_EXECPATH` and `CLAUDE_CODE_FORCE_TERMINAL_IMAGES=1` in the processes it spawns, even when the user did not set them (checked at runtime: all six were seen in a Claude Code 2.x session's child processes on 2026-11-16), so a `dotai run` started from a Claude Code session inherits them. `CLAUDE_EFFORT` is output only, set for Bash subprocesses and hooks (the input is `CLAUDE_CODE_EFFORT_LEVEL`); `CLAUDE_CODE_EXECPATH` is not in the reference. The reference, read again on 2026-11-16, documents five more as set by Claude Code only: `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN`, the parent session's inbox socket and its per-session token, exported to hooks and Bash commands, so an isolated session that inherits them could reach the parent's inbox; `CLAUDE_PID`, Claude Code's own process ID; `CLAUDE_CODE_BRIDGE_SESSION_ID`, set while the session has an active Remote Control connection; and `CLAUDE_JOB_DIR`, a background session's `~/.claude/jobs/<id>`. Of these, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN` and `CLAUDE_PID` were also seen at runtime in a Claude Code 2.1.309 session's child processes on Windows on 2026-11-16, together with `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ATTENDED` and `CLAUDE_CODE_VERSION`, which are not documented (`CLAUDE_CODE_ENTRYPOINT` may also be set by SDK callers). `dotai run` always removes fourteen: the four plugin and shell variables, the five session variables above but `CLAUDE_CODE_FORCE_TERMINAL_IMAGES`, and the five documented as set by Claude Code only. It removes five more only when `CLAUDECODE` shows a parent session, since the user or another program may set them: `CLAUDE_CODE_FORCE_TERMINAL_IMAGES`, a documented user input (draw mod `Image` elements as pictures in a terminal with the kitty graphics protocol); `TRACEPARENT`, a standard trace variable that Claude Code propagates to Bash, PowerShell and hook subprocesses (by default only with the direct Anthropic API); and `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ATTENDED` and `CLAUDE_CODE_VERSION`. Its note names each one removed, never its value. `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `AWS_BEARER_TOKEN_BEDROCK`, `ANTHROPIC_FOUNDRY_API_KEY`, `ANTHROPIC_FOUNDRY_AUTH_TOKEN` and `ANTHROPIC_AWS_API_KEY` authenticate instead of the login of the configuration directory; `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_MANTLE` and `CLAUDE_CODE_USE_ANTHROPIC_AWS` switch to another provider, and `ANTHROPIC_BASE_URL` and `ANTHROPIC_CUSTOM_HEADERS` change the endpoint and the headers of each request. `dotai run` passes them on with a warning that names each one set, never its value; the list is not exhaustive. The reference documents no `*_FILE_DESCRIPTOR` token variable.
- **Shared skills:** there is no shared skills folder; a variant that shares skills gets a link per skill of `~/.agents/skills` in `<dir>/skills/` ([0036](decisions/0036-shared-skills-per-variant.md)).
- **Same-name items:** a user skill wins over a project skill; a project subagent wins over a user subagent ([0023](decisions/0023-flat-profiles-and-layer-merge-rules.md)).

## agy, Google Antigravity CLI (1.4.7)

- **MCP:** user servers in `~/.gemini/config/mcp_config.json`. Project servers in `.agents/mcp_config.json` are started at runtime, although `agy mcp list` does not show them.
- **Plugins:** `~/.gemini/config/plugins/<dir>/`, marked by a `plugin.json`.
- **Skills:** global skills are read from both `~/.gemini/config/skills/` and `~/.gemini/antigravity-cli/skills/`. Skill discovery skips a directory junction there: a skill reached through a junction in `<dir>/config/skills/` is not listed, while a real skill directory next to it is; likewise `agy plugin validate`, which checks a plugin's skills as the loader reads them, counts a real skill directory under the plugin's `skills/` and not a junction to one (checked on 1.4.12, Windows). Symbolic links were not checked. There is no shared skills folder; a variant that shares skills gets a copy of each skill of `~/.agents/skills` in `<dir>/config/skills/` ([0036](decisions/0036-shared-skills-per-variant.md)). On its first run in a configuration directory, agy moves `antigravity-cli/skills/` to `config/skills/` and writes `config/.migrated`; on Windows it then fails to link the old path back, so dotai installs skills at `config/skills/` ([0031](decisions/0031-isolated-install-root.md)). In `SKILL.md`, agy ignores `allowed-tools`, `model` and unknown blocks, and honors `disable-model-invocation`.
- **Rules:** `.agents/rules/*.md` need a `trigger` in their frontmatter (`always_on`, `model_decision` or `glob` with `globs`); a rule without frontmatter is dropped with "Invalid rule trigger". agy reads both `AGENTS.md` and `GEMINI.md`, so the same content must not be in both.
- **Subagents:** the model of an agent definition is `inherit`, `flash` or `pro`.
- **Permissions:** a `permissions.deny` entry such as `read_file(<path>)` is enforced, even when permission prompts are skipped.
- **Settings:** user only, in `~/.gemini/antigravity-cli/settings.json`; there is no project settings file ([0025](decisions/0025-settings-as-per-harness-passthrough.md)).
- **Statusline command (Windows, 1.4.x):** quotes in `statusLine.command` are not stripped: with `powershell.exe ... -File "<path>"`, PowerShell gets the quotes as part of the path and fails on every refresh (`statusline_runner.go` in `cli.log`), while the same command with the path unquoted works. A bare `.sh` path runs through the file association, in a new console window, and fails. This matches how agy runs hook commands, through `cmd /c` with each `"` escaped as `\"` (see Hook commands below), but the statusline runs only in the interactive screen, so whether it also goes through `cmd /c`, and how it behaves on Linux and macOS, were not checked; dotai writes the path bare and refuses one with whitespace or a quote for agy ([0037](decisions/0037-tool-commands-resolved-per-os.md)).
- **Isolation:** the undocumented `--gemini_dir=<abs>` flag, which `dotai run` passes first. A relative value resolves against the home directory, so it must be absolute. `ANTIGRAVITY_GEMINI_DIR` appears in the binary but is ignored. With it, agy reads `<dir>/config/` (`agents/`, `rules/`, `skills/`, `hooks.json`, `mcp_config.json`), `<dir>/antigravity-cli/settings.json`, and `GEMINI.md` or `AGENTS.md` at `<dir>/` and `<dir>/config/`; the same content must not be in both. Authentication stays in the OS keyring, shared ([0018](decisions/0018-install-modes-and-mandatory-backup.md)). `agy --gemini_dir=<abs> --version` and subcommands after the flag work on 1.4.11.
- **Headless mode (checked on 1.4.2):** `agy -p --output-format json` prints `status`, `response`, `error`, `duration_seconds`, `num_turns` and `usage` (input, output, reasoning and cache tokens); `stream-json` also exists. An error is reported as `status: ERROR`; the exit code in `cmd` is not reliable. `--json-schema` and `agy models` also exist.
- **Model and effort (checked on 1.4.2):** `--model` sets the model. `--effort` (low to max) is accepted only on Gemini models, whose ids also carry the level (`gemini-3.8-flash-low|medium|high`); third-party models reject it with "--effort is not supported for model".
- **Encoding in `-p` mode (Windows, checked on 1.4.2):** non-ASCII characters in `response` arrive as `U+FFFD`, in both `json` and `stream-json` and with any console code page. Files that the agent writes keep them.

## OpenCode (v1 1.19.4, v2 2.0.30)

- **Versions:** v2 reads v1 configuration keys. rulesync 41.0.0 output (agents, commands, MCP as `mcp.servers`) loads on both.
- **Agent frontmatter:** unknown keys can leak into the provider request body. Output generated by rulesync strips them.
- **Skills:** `~/.agents/skills` is always read in v2, from `os.homedir()` (`USERPROFILE` on Windows). The undocumented `OPENCODE_TEST_HOME=<dir>` moves that home; `OPENCODE_DISABLE_EXTERNAL_SKILLS` does not exist in v2. `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` drops only the Claude Code skills. For a variant that shares skills, `dotai run` leaves `OPENCODE_TEST_HOME` out so that `~/.agents/skills` loads from the real home ([0036](decisions/0036-shared-skills-per-variant.md)).
- **Settings:** `model` is `provider/model`; a top-level `env` key is dropped silently; there is no statusline setting ([0025](decisions/0025-settings-as-per-harness-passthrough.md)).
- **Isolation (v2.0.30, Windows):** `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` are honored on Windows too; the temporary directory stays `%TEMP%\opencode`. `OPENCODE_DISABLE_CLAUDE_CODE=1` drops `~/.claude` and the `.claude` directories found above the working directory. `OPENCODE_CONFIG_DIR`, `OPENCODE_DISABLE_PROJECT_CONFIG`, `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS`, `OPENCODE_CONFIG` and `OPENCODE_CONFIG_CONTENT` also exist. `opencode debug paths` prints the directories it uses, `home` included ([0018](decisions/0018-install-modes-and-mandatory-backup.md)).
- **Walk-up:** from the working directory up to the root of the file system, with no stop, OpenCode collects `.claude`, `.agents` and `.opencode` of every directory. Rules files (`AGENTS.md`) are collected only up to the home directory: an `AGENTS.md` in the directory above the home was not loaded (checked on 2.0.30, Windows; see the [replace inventory](#replace-inventory)). So with a working directory under the home directory, `~/.agents/skills`, `~/.opencode` and `~/AGENTS.md` load whatever `OPENCODE_TEST_HOME` says; `OPENCODE_TEST_HOME` hides `~/.agents/skills` only for a working directory outside the home. Checked on Windows: the watcher subscribed to the real profile's `.agents\skills` with `USERPROFILE` and `OPENCODE_TEST_HOME` set elsewhere.
- **Global skills (checked on 2.0.30):** for each configuration directory (`$XDG_CONFIG_HOME/opencode` among them) OpenCode scans both `skill/` and `skills/` for `*.md` and `**/SKILL.md`; the frontmatter takes `name`, `description`, `metadata` and `disable-model-invocation`, so rulesync's `SKILL.md` loads. `opencode api skill.list` lists them, but they load after the server starts: the first answer of a fresh `--standalone` server can be empty. A server started with `opencode serve --port <n>` listed the pack's skill from `<isolated>/opencode/config/opencode/skills/commit-message/SKILL.md`.
- **Variables:** `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_CLI_CONFIG_CONTENT` (`cli.json`) and `OPENCODE_DB` point OpenCode at another configuration or database.
- **Background service:** most commands reach a background server on port 45278 (Windows) or 49374 (Unix), started on demand and left running; its URL, process and password are in `$XDG_STATE_HOME/opencode/service.json`. It starts in the home directory, so it fails with `ENOENT` when `OPENCODE_TEST_HOME` names a missing directory. Environment variables do not reach a service that already runs. `--standalone` runs a private server instead; on 2.0.30 it is taken by the default command and by `run`, `api`, `mini`, `models`, `stats`, `reload`, `session list|delete|export|import` and `auth list|login|logout|export|import|switch`, before or after the subcommand, and refused by the rest (`Unrecognized flag: --standalone in command opencode debug paths`). `debug config`, which does not take it, starts the background service.
- **Executable:** npm installs `opencode.cmd` on Windows, which runs `node_modules\@opencode\cli\bin\opencode.exe` next to it; the package is `@opencode/cli`.

The only configuration keys are `mcpServers`, when set, and those inside `projects`.
- **Classification of `plugins/synced/`:** recommended wiped with the rest of `plugins/`, since a fresh install recreates it from the account; whether a wipe loses anything the account does not restore is open for the maintainer.
- **Verified, interactive (logged in, `USERPROFILE` and `HOME` set to the test home, `CLAUDE_CONFIG_DIR` set to a directory inside it):** `~/CLAUDE.md`, at the root of the home directory, is not loaded as a user-level file for a working directory outside the home directory.
- **Verified, interactive (same setup, working directory under the home directory):** `~/CLAUDE.md` loads, as a project `CLAUDE.md` found by the walk-up from the working directory, while the `CLAUDE.md` of the configuration directory loads as the user-level one. So `~/CLAUDE.md` reaches every session whose working directory is under the home directory.
- **Unverified:** whether `~/CLAUDE.local.md` loads the same way.

### Claude Code home instructions (2.1.318, Windows)

How the home directory's instruction files reach an isolated Claude Code session, and how `claudeMdExcludes` skips them; the stream report was taken with the Claude Code of that day, the trial on 2.1.318.

- **Verified, stream report (Windows 11, `dotai run claudecode` isolated, `stream-json`, 2026-11-04, by the pack author):** the real `~/.claude/CLAUDE.md` also loads in an isolated session whose working directory is under the home directory: the walk-up reads both `CLAUDE.md` and `.claude/CLAUDE.md` in every directory above the working directory. With `claudeMdExcludes` in the isolated `settings.json`, the next session listed only the isolated `CLAUDE.md` and the project's, not the real one. That run set three forms of the pattern at once, so it did not tell which one matched; the next entry does.
- **Verified (Claude Code 2.1.318, Windows 11, 2026-11-04):** with `claude -p`, `CLAUDE_CONFIG_DIR` at a temporary directory, a fake home holding a marker in `CLAUDE.md`, `.claude/CLAUDE.md` and `.claude/rules/<name>.md`, and the working directory a project below it, the session reported all three markers, loaded by the walk-up. With `claudeMdExcludes` in the isolated `settings.json` naming `<home>/CLAUDE.md` and `<home>/.claude/CLAUDE.md` as absolute paths with forward slashes, in the case the directories have on disk (`C:/<...>/home/CLAUDE.md`), both were excluded, and `<home>/.claude/rules/**` excluded the rules. The same paths in lower case excluded nothing: **the match is case-sensitive**, on Windows too. So an isolated install writes the patterns for the home directory as it is on disk, its links followed and its case as on disk, and for the home directory as given when that differs.
- **`claudeMdExcludes` (documented, [memory](https://code.claude.com/docs/en/memory), read 2026-11-04):** glob patterns matched against absolute file paths, in any settings layer; the arrays of every layer merge. A managed `CLAUDE.md` cannot be excluded. An isolated install owns the key in `<dir>/settings.json` and lists `<home>/CLAUDE.md`, `<home>/CLAUDE.local.md`, `<home>/.claude/CLAUDE.md` and `<home>/.claude/rules/**`, absolute with forward slashes (`C:/Users/<user>/.claude/CLAUDE.md` on Windows), for each form of the home directory (on disk, then as given when it differs), after any patterns of the pack; a home directory whose path holds a glob character, extended ones such as `(`, `+`, `@` and `!` included, gets none, with a notice.

## Project scope inventory

What each harness reads in a project, for the project scope of [0041](decisions/0041-project-scope-local-and-untracked.md). Checked on Windows 11 on 2026-11-02 with non-interactive sessions in throwaway git repositories (`git init`, one commit), with every `CLAUDE*`, `XDG_*`, `OPENCODE*`, `GEMINI*` and `ANTIGRAVITY*` variable removed and `HOME`, `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` pointed at a temporary home; Claude Code with `CLAUDE_CONFIG_DIR` and a copied login, OpenCode with the four `XDG_*` variables, `OPENCODE_TEST_HOME` and `--standalone` (or `opencode serve --port <n>` for the API), agy with `--gemini_dir=<abs>` and the shared keyring login. Each file held a unique marker; the session was asked to list the markers in its context, and Claude Code's `stream-json` init message gave the loaded skills, agents, commands and model. A fact marked **model report** rests on the session's answer only. The repositories were under the real home directory, so OpenCode's walk-up also listed the real `~/.claude/skills` and `~/.agents/skills`; the test names did not clash with them. ### Hook commands

rulesync 41.0.0 renders `.rulesync/hooks.jsonc` per project to `.claude/settings.json` (`hooks`), `.agents/hooks.json` (a `rulesync` group with `SessionStart`, `PreToolUse`, `PostToolUse`, `PreInvocation` and `Stop`) and `.opencode/plugins/rulesync-hooks.js`. It skips `sessionEnd` and `beforeSubmitPrompt` for agy and `sessionEnd` for OpenCode, with a message. Checked with a PowerShell script in a directory with a space and one without, called as `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <path> <label>`, each run writing its own file, on the same versions as above.

| Command form | Claude Code | OpenCode | agy |
|---|---|---|---|
| Path in double quotes, `/` or `\`, with a space | runs | runs | fails: the quote reaches PowerShell as `\"`, part of the path |
| Bare path with a space | fails: split at the space | fails: split at the space | fails: split at the space |
| Bare path with `\`, no space | fails: bash drops the backslashes | runs | runs |
| Bare path with `/`, no space | runs | runs | runs |
| `echo x>> <file>` (shell redirection), path without whitespace | runs | runs | runs, with `\` or `/` (corrected; see agy below) |

- **Claude Code:** commands run through Git Bash on Windows. Hooks of one event run in parallel: two writing the same file collided. In `-p` mode `SessionStart`, `UserPromptSubmit`, `PreToolUse` (matcher `Bash`), `PostToolUse`, `Stop` and `SessionEnd` fired; `SessionEnd` ran and was also reported as "Hook cancelled" on stderr.
- **OpenCode:** the plugin runs each command through Bun Shell, a bash-like parser inside the process. `sessionStart`, `beforeSubmitPrompt`, `preModelInvocation`, `postToolUse` and `stop` fired. `preToolUse` with matcher `Bash` did not: the tool is `bash`, and the generated test is a case-sensitive regular expression.
- **agy:** commands run through `cmd /c`, as agy's own hook docs say, with the whole command passed as one argument quoted by Go's rules, so every `"` reaches `cmd` as `\"`. Checked on 1.4.12, Windows 11, with `SessionStart` hooks in `<dir>/config/hooks.json` and one `agy --gemini_dir=<abs> -p` session per batch, each hook writing a file: `echo %OS% > <file>` wrote `Windows_NT`; `echo first> <a> && echo second> <b>` wrote both files; `echo pipe-ok | findstr pipe > <file>`, `echo x>> <file>` with `\` and with `/` all ran; `echo one   two> <file>` kept the three spaces, so the command is not split at whitespace; `echo "a b"> <file>` wrote `\"a b\"`; `powershell.exe ... -File <path> "a b" %OS%` gave the script three arguments, `"a`, `b"` and `Windows_NT`. An earlier entry here said the commands ran without a shell, split at whitespace; that was wrong, and an earlier `echo x>> <file>` failure was not reproduced. The quoting rule of [0037](decisions/0037-tool-commands-resolved-per-os.md) still holds: no double quotes and no whitespace in a path for agy. `cli.log` names each hook `jsonhook__rulesync_<Event>_<group>_<index>`. `SessionStart`, `PreInvocation`, `PostToolUse` and `Stop` fired; `PreToolUse` with matcher `Bash` did not, since agy's shell tool has another name.
- **agy `SessionStart` output (1.4.12, Windows 11):** stdout must be JSON. In one `-p` session with four `SessionStart` hooks, one printing `{"injectSteps":[{"systemMessage":{"systemMessage":"<marker>"}}]}` and three printing a plain-text marker (from a PowerShell script and from `echo`), the model, asked for the markers in its context, gave only the JSON one; `cli.log` logged each plain-text hook as `failed to unmarshal result ... via protojson`. Plain text does not reach the model.
- So a hook that runs a tool needs the quoting rules of 0037 for its harness: double quotes for Claude Code and OpenCode, a bare path without whitespace for agy. Matchers name each harness's own tools.

## Mods

How Claude Code loads a mod, for the mods of [0027](decisions/0027-loose-files-and-plugins-only-for-mods.md) and [PACK-FORMAT](PACK-FORMAT.md#mods). The facts come from the official Claude Code docs, read on 2026-11-02 ([skills](https://code.claude.com/docs/en/skills), [plugin loading](https://code.claude.com/docs/en/plugins/loading), [mods overview](https://code.claude.com/docs/en/plugins/mods/overview), [mods reference](https://code.claude.com/docs/en/plugins/mods/reference), [plugin components](https://code.claude.com/docs/en/plugins/components), [hooks](https://code.claude.com/docs/en/hooks)). Those marked **verified** were checked on Claude Code 2.1.316, Windows 11, with an isolated `CLAUDE_CONFIG_DIR` and no session: `dotai apply --profile web` of the example pack in a test repository, then `claude plugin list` and `claude plugin validate .claude/skills/hello` in the project. The others are documented, not session-checked.

- **Where, verified:** a folder `.claude/skills/<name>/` with a `.claude-plugin/plugin.json` loads as the plugin `<name>@skills-dir`: `claude plugin list` showed `hello@skills-dir`, scope `project`, version `0.1.0`, status `loaded`. Documented: it brings its agents, hooks and MCP servers; it is read only from the session's primary working directory, with no search of parent directories, and `.claude/plugins/` is not scanned.
- **Trust, verified:** such a plugin loads only when the workspace is trusted, `projects["<path with forward slashes>"].hasTrustDialogAccepted: true` in the `.claude.json`. Without it the plugin is skipped, "skipped because this workspace was not trusted when plugins were scanned. After accepting the trust dialog, run /reload-plugins". Documented: `-p`, or a trusted parent folder, is not enough.
- **What makes a mod, verified in part:** a plugin whose `hooks/hooks.json` has `"modules": ["./register.js"]`, each path relative to `hooks.json`; `claude plugin validate` passed on the example mod and reported `./register.js hooks: session.start` and `calls: $.ui.status`, and warned only that its `plugin.json` had no `description` and no `author`, which dotai now writes. Documented: the module is an ES module that exports `register(on, options)`, in `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts` or `.tsx`, with no build step; a mod adds no required field to `plugin.json`; `hooks.json` may also carry settings-style `hooks`.
- **Checking a mod:** `claude plugin validate <dir>` reads the manifest and the module as Claude Code will, and reports the module's hooks, the calls it makes and what Claude Code would refuse; a pack author can run it on the installed `.claude/skills/<mod>/`.
- **Names, documented:** inside the plugin, skills are `/<plugin>:<skill>`, agents `<plugin>:<name>` and MCP servers `plugin:<plugin>:<server>`; a `SubagentStart` or `SubagentStop` matcher for a plugin's agent needs `^<plugin>:<agent>$`.
- **Turning it off, documented:** `enabledPlugins["<name>@skills-dir"]: false`, which `.claude/settings.local.json` can set over the team's settings; `disableAllHooks`; `--safe-mode`.
- **Version, documented:** mods need Claude Code 2.1.287 or later, in the terminal.
